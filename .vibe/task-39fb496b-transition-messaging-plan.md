# 验收状态提示修复计划

## 目标

将验收相关的状态拒绝提示改为可执行的中文说明：明确当前状态、允许的状态和下一步动作，避免用户只看到“当前状态不支持此操作”。

## 范围

- 覆盖最终验收、退回修改和逐项验收的状态不匹配场景。
- API 为工作项状态拒绝提供结构化上下文；不暴露非状态类内部错误。
- Web 统一将状态上下文翻译为中文，并在验收入口预先说明何时可操作。
- 不改变状态机规则、权限模型、验收结论或既有任务数据。

## 实施步骤

1. 在 API 的工作项状态拒绝错误中携带当前状态、允许状态与下一步动作，并在错误响应中传递这些受控字段。
2. 在 Web API 客户端为 `INVALID_TRANSITION` 增加结构化中文格式化；未知或非结构化错误继续使用安全兜底文案。
3. 在最终验收与逐项验收界面按当前任务状态显示可操作条件；非 `in_review` 状态不发送验收请求。
4. 先新增失败测试，分别覆盖客户端提示、最终验收入口和逐项验收入口；再实现最小代码使测试通过。
5. 运行相关 Web/API 测试、类型检查和构建，并提交本轮报告供人工验收。

## 依赖与边界

- 当前状态机仍要求任务先提交成功执行报告进入 `in_review`，再允许最终验收。
- 已完成任务需要先重新打开，才能改动验收结果。
- 无审核权限仍由现有权限提示处理，不伪装成状态错误。

## 风险

- 全局错误格式化会影响所有 `INVALID_TRANSITION` 请求；仅消费 API 提供的受控状态字段，未知错误不得显示服务端原始信息。
- 前端预防性禁用不能取代服务端校验，服务端规则必须保留。

## 测试与验收映射

- 状态限制的文案：客户端测试断言当前状态、允许状态和下一步动作。
- 验收项状态与证据：任务未进入 `in_review` 时逐项验收不可提交且显示条件；进入后保持既有保存能力。
- 最终验收：非 `in_review` 时显示进入待审核的路径；`in_review` 时保留批准与退回。
- 任务不能被误完成：服务端状态机测试和既有验收测试继续通过。
