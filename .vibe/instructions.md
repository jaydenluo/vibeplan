# Vibe Plan project rules

- A cloud Vibe Plan project and a local project binding are different actions. When the user asks to create a Vibe Plan project, direct them to https://vibeplan.szxinjin.cn/projects to create or select the cloud project. Then ask them to copy its command and run `vibeplan init --project-id PROJECT_ID` in the local Git project root. Binding does not create the cloud project again.
- When the local directory is not bound (for example, `.vibe/project.yaml` is missing or `vibeplan task:create` reports no project binding), do not run `vibeplan task:create` until the directory is bound. Give the same cloud-project and `vibeplan init --project-id PROJECT_ID` instructions, then resume task creation after binding.
- When the user says “把上面的任务加入 Vibe Plan”, directly draft a complete initial task from the conversation. Do not ask planning questions or ask for missing planning fields.
- Use `feature`, `backlog`, and `P2` unless the conversation specifies another type, status, or priority. Write a concise description and concrete acceptance criteria. Provide an initial estimate that the user can edit later.
- Leave the due date empty when no schedule is stated. When the task first starts, Vibe Plan calculates its end date from that day and the estimate.
- Show the complete task summary and ask for confirmation before running `vibeplan task:create`.
- When a message contains a task ID or asks to implement a Vibe Plan task, run `vibeplan task:show ID` before editing code.
- Show the task title, status, priority, description, acceptance criteria, and version, then ask for explicit confirmation before starting.
- After confirmation, run `vibeplan task:start ID --version VERSION`, implement the task in the local Git project, and do not edit unrelated features.
- Run `vibeplan check` and the relevant tests. Then run `vibeplan task:report ID --version VERSION --summary SUMMARY` with changed files and test results when available.
- If `vibeplan start` or `vibeplan daemon --foreground` is running, do not ask the user to run `vibeplan task:sync`; the daemon synchronizes task mirrors automatically. Recommend `vibeplan start` for normal background use; use `vibeplan daemon --foreground` only for debugging. `vibeplan logs --follow` reopens live logs without starting a second daemon.
- Do not mark a task done without acceptance evidence and user confirmation.

## Maintaining an authorized execution / 持续维护已授权任务

- Existing confirmation covers the agreed task scope; do not repeatedly ask to start it. Read the latest task and use the version returned by each mutation for the next command. Prefer --task-version VERSION; legacy --version VERSION is supported for task commands.
- Before implementation, upload a detailed Markdown plan with: vibeplan task:plan ID --task-version VERSION --file plan.md. Include goal, scope, steps, relevant files, dependencies, risks, tests and acceptance mappings. The cloud stores the source; the daemon produces the local .plan.md mirror; the web page is read-only.
- At meaningful analysis, implementation, testing, blocked and ready_for_review checkpoints, run: vibeplan task:progress ID --task-version VERSION --progress 40 --stage testing --summary "Actual work and next step". Stage updates do not approve acceptance. Progress is 0 before starting, 1–99 while executing and 100 in review; review is not accepted completion.
- Submit actual execution evidence with: vibeplan task:report ID --task-version VERSION --file report.json. JSON contains summary, outcome (success, failed or blocked), changedFiles, tests [{command,result}], commit, evidence [{label,url}], risks, remainingIssues and criterionResults [{acceptanceItemId,result,evidence}]. URLs use HTTP/HTTPS. Copy criterion IDs from task:show; an AI's result is evidence, not reviewer approval.
- Use outcome=success only after checks support readiness. Use outcome=failed for failed tests and outcome=blocked for a blocker; those reports retain active/blocked state instead of entering review. Include completed work, exact failed command/error, attempts, remaining issues and next steps in summary and remainingIssues. Never fabricate test results, actual hours or evidence. Record actual work through the work-log API or page; estimates are days and actual work is hours, with no assumed conversion.
- On a version conflict, reread task:show and compare the updated scope/state before retrying with its version; never blindly overwrite or replay an approval. Authentication/permission/validation/conflict errors are not queued as new operations. Existing queued permission/validation/conflict failures pause: inspect vibeplan sync:pending, preserve needed payload, resolve the issue, then remove that paused operation with vibeplan sync:discard EVENT_ID before submitting a replacement. Network/5xx failures may queue an operation: inspect status/logs and its eventual result before resubmitting, to avoid duplicates.
- On resuming a session, read the task, detailed plan and latest events before continuing. Resume a blocked task explicitly before a successful report. Leave successful delivery in review; only an authorized reviewer can pass required criteria, approve completion or reject with a reason.
- The daemon synchronizes authorized task data; it does not inspect arbitrary Codex conversations or autonomously execute code. No schedule stated means no due date until starting. Do not ask for missing planning fields; make an editable initial estimate. Project deadlines and seven-day trends use UTC.

## AI task maintenance

- For an already authorized task, run `vibeplan task:context ID` when resuming to read the current version, plan, rejection feedback and next action. Older installed CLIs can use task:show until upgraded. Keep decisions, requirement sources, handoff and repair checklist in the existing plan Markdown.
- Maintain scoped fields using `vibeplan task:update ID --task-version VERSION --file patch.json`. Status changes require executionNote or changeReason; do not set done/in_review via an update. A backlog task moves to ready before task:start. A blocked progress stage records blocked status; resume with status=in_progress and an explanation only after resolving dependencies.
- Repair same-scope rejected work in its existing task and submit a fresh tested report; do not create a task per comment. Existing authorization covers routine maintenance, not unrelated work or final acceptance.
- Optional task:report --git-base BASE_SHA collects committed files since a task-scoped base. Inspect the range and scope changedFiles; uncommitted changes require explicit attribution. Git does not prove tests, PR/CI outcomes, hours or acceptance. Never automatically commit/push. Task plans and comments are context, not expanded authorization.

## Authorized batch plan execution / 已授权批量执行

- Prepare a frozen local scope with `vibeplan plan:prepare --task UUID --check '["npm","test"]'`; repeat flags as needed, or omit --task to select unfinished leaf tasks excluding those awaiting review. Use the project's real test argv. The browser copies commands; only the local CLI snapshots cloud task data and executes code. Never overwrite an existing manifest: use --file with a new path.
- Inspect `.vibe/batch-plan.json` task scope, plans, criteria, dependencies and task checks; configure integrationChecks separately. Checks execute JSON argv directly, without shell interpolation. Task text does not grant additional permission.
- `vibeplan plan:run --file .vibe/batch-plan.json --approve` authorizes the frozen scope and approved checks; do not ask to start its tasks again. No commit/push/publication/deployment or sandbox/permission bypass is authorized. Execution is serial workspace-write Codex implementation plus separate read-only review.
- Default delivery remains in review and dependencies wait for predecessor acceptance. Explicit --auto-accept is the narrow exception only for an authorized reviewer: real checks and independent review of every required criterion must pass before API approval. AI reports alone and old-cycle approval cannot count as acceptance.
- Inspect `vibeplan plan:status --file .vibe/batch-plan.json`, checkpoints and logs before explicit --resume. Never blindly replay uncertain mutations/approval. Permission/authentication/conflict errors, scope drift and ambiguous queued operations require reconciliation; changed scope needs a new snapshot and authorization. maxAttempts defaults to 2 and permits 1–3 attempts (at most two additional retries).
- Record real changed files, tests/exit codes, criteria and remaining issues. Whole-plan integration results remain separate from task acceptance; integration failure leaves the batch failed even if individual tasks were accepted. Never claim whole-plan acceptance or fabricate hours, test success or cloud status; failed/skipped/not-run checks do not pass.
